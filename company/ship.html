Shipping Almari

The ordered steps to build and launch on Android and iOS — the commands, the gates, and how you know each one worked.

The Workroom · The Tech Workbench · The runbook · The app

The Tech Workbench holds what has to be done and who owns it. This holds how, in order, with the commands. If the two ever disagree, the board is the plan and this is the recipe — fix the recipe.

Two rules make the rest of it work. The shared layer blocks everything, so it is built once, by one person, before either platform track starts. And iOS and Android are not serialised against each other — they are both serialised against that shared layer, which is the entire reason this is one codebase and not two.

Green — how you know the step actually worked. If you cannot show this, the step is not done.
Carmine — the trap. Each one here has bitten somebody; several are unrecoverable.
Gold — a gate you do not control. Start it early; you cannot compress it.

Part 0 — Before a single line of port code

Week 1 · in parallel

None of this is porting. All of it is the difference between a launch and a scramble, and every item is cheap now and expensive in October.

Make the repository safe for four people

Today CI runs only on push to main. Three developers are about to open pull requests into a repository where nothing checks them until after they are merged and live.

# .github/workflows/ci.yml — a second workflow, PRs only
on: { pull_request: { branches: [main] } }
jobs:
  verify:
    steps:
      - run: npm ci
      - run: npm run lint
      - run: npm run typecheck
      - run: npm run test:migrate && npm run test:demo && npm run test:intake
      - run: npm run build

Then make those checks required in branch protection, and commit a LICENSE before anyone gets write access — a merged outside pull request into an unlicensed repo puts unassigned third-party copyright into the company's only asset.

Done when a deliberately broken pull request goes red and cannot be merged.

Pin the toolchain and do not move it again until launch

Xcode 26 has been mandatory since April 2026 and Capacitor 8 requires it. Xcode 27 is coming and Capacitor 8.5 already changed iOS behaviour to suit it. A toolchain that moves under a four-person team during a first launch costs days nobody budgeted.

node   22.x      # Capacitor 8 requires it; CI is still on 20
capacitor 8.5.x  # exact, not ^
xcode  26.x      # committed into the CI config
gradle / AGP     # whatever cap 8.5 ships with, unchanged
Trap Do not install an Xcode 27 beta on the only Mac before launch. Schedule the UIScene and Capacitor 9 migration as post-launch work with its own test gate.

Choose the package identifier — this one is permanent

The package name and bundle identifier can never be changed. The store listing name can be changed any day. So keep the brand out of the identifier, and the trademark opposition window stops being able to cost you the listing, the reviews and the install base.

package / bundle id   in.<company>.wardrobe   # permanent, brand-free
store listing name    Almari                  # changeable, any time
Trap Free to paid is also permanent on Play. Once an app has been offered free it can never be sold, and the package name is burned. Set a price before the first release to any track, internal included.

Part 1 — The shared layer

Weeks 1–3 · blocks both platforms

About 85% of the port lives here, and neither platform track can start until it lands. One person. Merged before anything else begins. If you serialise nothing else in this project, serialise this.

Put an interface in front of every read and write

Storage is touched in 25 places across 9 files. Until that is one interface, the photo pipeline, the migration and both platform integrations are all blocked on each other.

// src/lib/storage/index.ts
export interface StorageAdapter {
  readWardrobe(id: string): Promise<Wardrobe | null>;
  writeWardrobe(id: string, doc: Wardrobe): Promise<void>;
  writePhoto(garmentId: string, blob: Blob): Promise<string>;  // returns a RELATIVE path
  photoUrl(path: string): string;
  readSetting(k: string): Promise<string | null>;
  writeSetting(k: string, v: string): Promise<void>;
}

Two implementations: web.ts over localStorage, native.ts over Capacitor Filesystem and Preferences. Nothing else in src/ touches storage directly, ever again.

Done when the existing Node harnesses run green against a fake adapter, and grep for localStorage outside storage/ returns nothing.
eng1

Unify the three intake paths behind one resize

The cut-out path caps images at 512px. The manual add path does no resizing at all — a raw phone JPEG goes straight to base64. Quota dies at roughly four garments, today, on the web. Fix it before the migration, or the migration carries the bug across.

Done when a test fails if any intake path writes an unresized image, proven with a modern phone camera JPEG.
eng1

Move photographs onto the filesystem

Every garment photo is currently a base64 PNG inside one JSON blob, and the whole application state — every photo included — is rewritten on every change. Capacitor documents WebView storage as transient: the OS reclaims it under disk pressure. This is a data-loss problem wearing a performance problem's clothes.

photos/<garmentId>/full.jpg    1600px, q0.82   → Directory.LibraryNoCloud
photos/<garmentId>/thumb.jpg    400px, q0.75   → Directory.LibraryNoCloud
wardrobes/<id>.json             metadata only  → Directory.Data

Read them through Capacitor.convertFileSrc() so the bytes never cross the JS bridge. Write the JSON as .tmp then rename — a partial write during an app kill is the one way a document store loses everything.

Trap Relative paths only. The iOS container UUID changes across updates and restores, so an absolute path is a bomb that goes off on somebody else's device months later. And photos go in LibraryNoCloud, not Data — on iOS Data maps to Documents and is iCloud-backed, so every wardrobe would silently spend the user's iCloud quota. Never store PHAsset identifiers: they are nil under limited access, and revocable.
eng1

Write the migration test before the migration

The product promise is that the data is yours, permanently. A migration that silently drops wears or photographs is worse than any store rejection, and on iOS you cannot hot-fix it. A tester who loses a wardrobe is a permanent reputational event in a four-person company.

1. corpus: a real 300-piece wardrobe with photographs
2. force a full JSON export BEFORE the first migration runs
3. keep the pre-migration payload until the app has opened twice
4. round trip: export from device → import into web → diff
Done when the test exists and fails, before the migration code does. This is the gate for alpha round one — if it fails, the alpha does not happen.

Do not adopt SQLite

The plan of record said SQLite; the review reversed it. Almari has no queries — one JSON document per wardrobe, no joins, no partial loads. Meanwhile @capacitor-community/sqlite is now maintained by someone selling a closed competitor, carries an unanswered "database corrupted and cleared" issue, and its iOS location setting silently excludes the database from backup and device transfer.

Revisit when a real wardrobe crosses ~2,000 garments or launch-time parse exceeds 100ms on the P90 device. Measure; do not guess.

Done when the decision is written into docs/32 and the board rows that still say SQLite are corrected, so nobody re-adopts it by reading a stale task.

Part 2 — Android

Ships first · builds on Windows

Android goes first, and the reason is not Google — it is that an Android release can be built, signed and uploaded from the machines this team already owns.

Set the SDK levels, and understand what one of them costs

// android/variables.gradle
minSdkVersion    = 26   // up from Capacitor's 24
targetSdkVersion = 36   // required for new apps from 31 Aug 2026

On Android 7–9 the WebView is Chrome — permanently frozen and unpatched. For an app that is entirely a WebView, 24 → 26 deletes two OS generations of dead engine for about half a percentage point of reach.

Trap API 36 removes the edge-to-edge opt-out entirely. That makes safe-area handling launch-blocking web-layer work, not a manifest line. Budget days, not the hour it looks like.
eng2

Generate the upload key and store it in three places

keytool -genkeypair -v -keystore upload.jks -alias upload \
  -keyalg RSA -keysize 2048 -validity 10000

base64 -w0 upload.jks > upload.jks.b64   # → GitHub secret

Password manager, an encrypted offline copy, and CI secrets. Never in the repository. Play App Signing means a lost upload key is recoverable through support — document that path before you need it.

Done when a second person, on a different machine, has produced a signed bundle from the stored copy without asking anyone for help.
eng2

Ship with zero dangerous permissions

Capacitor's Camera plugin already uses the Android Photo Picker and needs no permission at all unless saveToGallery is set. A permission prompt on an app whose entire pitch is that it does not want your data is a self-inflicted wound.

# CI assertion on the MERGED manifest, not yours
! grep -q "READ_MEDIA_IMAGES\|READ_EXTERNAL_STORAGE" \
    android/app/build/intermediates/merged_manifests/**/AndroidManifest.xml
Done when CI fails the build if any plugin contributes a dangerous permission.

Pipeline to the internal track

Internal testing has no review, goes live in minutes, seats 100, and testers get the paid app free. It is the only track this launch needs. Closed and open testers would have to buy the app, and an organisation account is exempt from the 12-tester closed-test requirement entirely.

./gradlew bundleRelease          # .aab, not .apk
# → upload to the internal track via GitHub Actions
Trap Use the $25 hedge account and a throwaway package for pipeline work. The real package must have a price set before its first release of any kind.

Test on the real matrix, not the emulator

A WebView app breaks on ColorOS, One UI and HyperOS in ways no emulator shows: aggressive background killing, WebView version skew, storage cleaners that delete app files the OS said were safe. Prove a wardrobe survives an OEM cleaner before an external tester finds out for you.

Done when 60fps scrolling with 100+ garments on the low-RAM device, and a wardrobe survives a forced cleanup on each OEM skin.

Part 3 — iOS

Behind Android, on Apple's clock

The engineering here is not harder. The waiting is. Enrol as an Individual for $99 in week one so every piece of engineering, signing and TestFlight work can proceed while the organisation paperwork grinds — that $99 is the best-value line in the plan.

Permission strings that a reviewer will accept

Vague usage strings are a rejection. Say what you do with it, in the user's language.

<!-- ios/App/App/Info.plist -->
<key>NSCameraUsageDescription</key>
<string>To photograph a garment for your wardrobe. Photos stay on
this device.</string>
<key>NSPhotoLibraryUsageDescription</key>
<string>To add a photo you already have to a garment. Photos stay
on this device.</string>

Use PHPickerViewController for library access — it needs no permission at all.

Trap A string that says only "this app needs camera access" is a rejection under 5.1.1. Say what the data is used for and where it goes, and make sure the sentence stays true after the anthropic.ts decision.
eng3

The privacy manifest, in the same commit as the plugins

A missing or wrong manifest is an upload-time rejection — ITMS-91053 — discovered at the worst possible moment. @capacitor/preferences uses NSUserDefaults, which is a required-reason API.

<!-- ios/App/App/PrivacyInfo.xcprivacy -->
NSPrivacyTracking            false
NSPrivacyTrackingDomains     (empty)
NSPrivacyCollectedDataTypes  (empty)
NSPrivacyAccessedAPITypes    CA92.1   # UserDefaults
Done when a throwaway upload to App Store Connect validates — do this in week seven, months before it matters, purely to surface errors early.

Signing that survives one Mac dying

fastlane match init
fastlane match appstore          # private, encrypted git backend
match(type: "appstore", readonly: is_ci)

Store MATCH_PASSWORD, the App Store Connect .p8, the Key ID and the Issuer ID in the team password manager — the .p8 cannot be downloaded twice. Add a second person to App Store Connect as Admin.

Trap One Mac, one enrolment device, one person who knows the setup: the bus factor is one across hardware, credentials and knowledge. Two people must have run a release end to end before launch.

Build the rejection defence before the first submission

A WebView wrapper in a populated category from a brand-new account is the exact profile guidelines 4.2 and 4.3(b) target, and 4.3(b) was rewritten in June 2026 into an ongoing removal power. This is the highest-probability failure on the whole iOS track, and it is entirely mitigable with two weeks of native work. It is not polish.

· a WidgetKit home-screen widget
· Share Sheet intake
· an App Intents / Siri shortcut
· Files-app export via UIDocumentPicker
· haptics on the two-tap log

Name every one of them in the Notes for Review, and state plainly that all assets ship in the bundle and the app makes no network requests.

Trap A widget needs a shared App Group container to read photographs. That interacts with the LibraryNoCloud rule from step 1.3 — resolve the container question before starting, or the widget cannot read a single image.

Part 4 — The day you ship, and the week after

Both stores

Know how a crash reaches you

The contract forbids telemetry, and the plan honours it — which means that when the app crashes on a stranger's phone, nobody will ever know. Both stores surface crash data without any SDK: Android vitals, Xcode Organizer. Neither collects anything from the user, so both are compatible with the contract. Somebody has to opt in and then actually look.

Trap Archive the dSYMs and mapping.txt for every single release. Without them the reports are unreadable noise, and you cannot generate them after the fact.
hmops

Have somewhere for people to write to

Both stores require a support contact before submission, and with no telemetry a person writing in is the only way you will learn anything is broken. A monitored address — not a personal inbox — a one-page help site, a written refund position for each store, and a named person who answers reviews.

Gate This blocks submission on both stores, and the free web users will write to it too — more of them, permanently, than the paid app produces. Decide what you owe them before the address goes live.
ops

Roll out slowly, and keep the way back

Play      staged rollout, 20% for 48 hours, then widen
Apple     manual release, phased over 7 days
Both      a pre-staged rollback build, already uploaded
Trap Neither store lets you un-ship. Play's halt only stops further rollout; everyone who already has the bad build keeps it. The rollback is a new version, so it must be built and ready before you need it.
opseng2eng3

Never touch these two settings again

server.hostname
server.androidScheme

Changing either after release changes the WebView origin, which orphans every user's stored data with no error and no recovery. It is a worse one-way door than the three the plan lists, because it does not look like one.

Trap Put a comment in capacitor.config.ts saying exactly this, next to both values. The person who eventually changes one will not have read this page.
